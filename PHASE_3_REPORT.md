# Phase 3 Report

## Architecture Implemented

Phase 3 adds a read-only, market-anchored model layer alongside the existing deterministic
arbitrage scanner. The implementation is intentionally separate from Phase 2 arbitrage storage:

- Arbitrage opportunities remain deterministic and use `PAPER TRADING`.
- Model expected-value opportunities use `MODEL OPPORTUNITY`.
- Directional model simulations use `MODEL PAPER TRADE`.
- Simulation data remains labeled `SIMULATION`.

No live order submission, wallet, signing, deposit, withdrawal, or autonomous trading code was
added.

## Dataset Definition

The first complete workflow uses deterministic historical fixture snapshots generated by
`PredictionService.build_historical_dataset()`. Every row has:

- Market ID, exchange, category, prediction timestamp, close timestamp, feature timestamp.
- Best bid, best ask, midpoint, spread, last traded price.
- Multi-window price, volatility, volume, spread, imbalance, high-low, and divergence features.
- Liquidity, depth, cross-platform equivalent price, related-market probability, market age,
  update count, freshness, and missing indicators.
- Resolution outcome stored only as the label, outside the feature payload.

## Feature Definitions

Feature schema version: `phase3.v1`.

Lookback windows implemented: `1m`, `5m`, `15m`, `1h`, `6h`, `24h`, `7d`.

Each window includes price change, log return, realized volatility, volume change, spread change,
imbalance change, high-low range, distance from recent high/low, cross-platform divergence, and
trend consistency.

Financial logic uses `Decimal`. Conversion to `float` happens only in the scikit-learn training
and inference boundary.

## Leakage Protections

- Feature timestamps cannot exceed prediction timestamps.
- Market close timestamps must be after prediction timestamps.
- Resolution outcomes are rejected if they appear in features.
- Train/validation splitting is grouped by market ID.
- Validation is chronological by market close timestamp.
- Calibration is fit only on held-out validation predictions.
- The stacker path records held-out component predictions or explicit fallback averaging.

## Models Trained

Implemented behind a typed prediction-model interface:

- Market-implied probability baseline.
- Logistic regression.
- HistGradientBoostingClassifier gradient-boosted model.
- Market-anchored ensemble combining market midpoint, logistic, boosted, and cross-platform price.
- Calibration layer using Platt scaling for small held-out datasets and isotonic when enough data
  exists.

The dependency used locally is `scikit-learn>=1.9.0`.

## Validation Methodology

The current workflow uses deterministic fixture data and a grouped chronological holdout. Metrics
reported include Brier score, market baseline Brier score, log loss, ROC AUC when valid, accuracy,
calibration error, average predicted edge, prediction count, category counts, and exchange counts.

Models are registered as `candidate`; manual approval is required before predictions can create
model paper trades.

## Baseline Comparison

The model registry stores comparison against the raw market midpoint baseline. The current fixture
run is an implementation demonstration, not evidence of profitability.

## Model Registry Status

Registry table: `prediction_models`.

Supported statuses:

- `candidate`
- `approved_for_paper`
- `rejected`
- `retired`

Only `approved_for_paper` models can generate model predictions that lead to paper trades.

## Paper-Trading Settings

Defaults are conservative:

- 0.5% maximum paper bankroll per normal model trade.
- 1% maximum for highest-confidence model trades.
- 2% maximum exposure per event setting.
- 5% maximum exposure per category setting.
- 10% fractional Kelly multiplier.
- 25 maximum open model positions.

## Risk Limits

Implemented checks include stale data, missing approved model, low confidence, high uncertainty,
wide spread, insufficient liquidity/position size, minimum expected edge, and minimum expected ROI.

## Known Limitations

- Current training data is deterministic fixture data, not a large resolved live historical corpus.
- Live model opportunities should remain no-trade or sparse until enough resolved historical
  snapshots are collected.
- External structured-data providers and LLM forecaster interfaces are not enabled in the first
  implementation.
- The stacker uses explicit fallback averaging when held-out data is too small for a robust
  regularized stacker.
- Reported fixture metrics are engineering validation, not profitability evidence.

## Recommended Data-Collection Period

Collect several weeks to months of market/order-book snapshots and resolved outcomes before using
model-based paper-trading results for research conclusions. Require out-of-sample performance
against market midpoint and executable-price baselines before considering any Phase 4 expansion.

## Criteria For Phase 4

- A materially larger resolved historical dataset.
- Category-specific validation with enough markets per category.
- Stable calibration tables with meaningful sample sizes.
- Model paper-trading performance that beats market baselines out of sample.
- No unresolved leakage test failures.
- Continued read-only operation unless a separate, explicit live-trading safety design is approved.
